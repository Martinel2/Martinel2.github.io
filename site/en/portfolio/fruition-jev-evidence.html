CASE 01Fruition / AI Agent, RAG, Jev

RAG evidence selection: answer accuracy 71.7% → 93.0%, evidence sufficiency 95.4% on a fixed set

Fruition answers from uploaded documents, so I thought wrong evidence would make the whole answer untrustworthy. After seeing Jev improve request routing, I applied it to evidence selection. I then re-evaluated on a set I wrote and reviewed with my team, confirmed answer accuracy of 71.7% → 93.0% under identical conditions, and fixed what the evaluation exposed.

01 Background

The existing hybrid search missed evidence the answer needed, or attached evidence to questions that had no answer. Since finding and delivering accurate information from documents is the core of this project, I analyzed results at each step of the pipeline. The right evidence was always among the candidates but did not make the top 8, so evidence for 76 of 90 questions was never selected. We needed a step that picks the needed evidence from candidates and says so when there is none.

What solving it enables

If the evidence is wrong, the whole answer cannot be trusted, and users who lose trust do not come back. Giving the needed information with accurate evidence is the core of this product, so accuracy has to be high for users to trust it, keep using it and pay again.

02 Experiments and improvements

  1. Routing comparison and the decision to try RAG

    Problem Some questions were misclassified as document edits, leading to the wrong action. Task types and additional conditions needed to be selected more accurately and quickly.

    Experiment and result Applied Jev, a choice-based decision model released on September 14, to routing questions, document edits, document creation and folder organization. Across 98 requests, correct task types and additional conditions totaled 77 for the existing JSON approach, 63 for GPT-5-nano given the same options, and 81 for Jev. The existing approach is the original service setup, where GPT-5-nano wrote the task type and conditions itself as JSON; Jev and the GPT-5-nano comparison instead picked one of the valid combinations given as options. Against it, median decision time fell from 8.967s to 0.658s and API cost on the same 100 questions fell from about $0.0891 to $0.0408. GPT-5-nano given the same options cost about $0.1027.

    Decision It showed promise on accuracy, speed and cost. Since choosing evidence is also picking one out of many, I wondered whether it could handle the evidence selection hybrid search could not, so I built an evaluation set first and ran experiments. I chose Jev for two reasons. First, having GPT pick evidence cost about 2.5× more with the same options, and took longer to decide. That was a heavy burden for a step that checks hundreds of candidates per question. Second, re-ranking by adjusted search scores stayed at similar scores no matter which hybrid weights and RRF values I tried. Embeddings sometimes failed to separate differences in Korean phrasing, so I judged that fitting one weight to questions from different fields would gain little. Instead of polishing the ranking further, I had Jev judge the needed evidence directly from the gathered candidates.

  2. Full-corpus inspection: evidence coverage on all 90 answerable questions

    Problem Searching with the original question and weighting semantic scores more raised the number of questions, out of 110, whose right evidence ranked first from 50 to 57. But the experiment was biased, and reliably picking the needed evidence for new questions was still unsolved. Answering general questions reliably is the core of the project, so this part's quality had to improve.

    Experiment and result To see whether Jev could find evidence that search missed, I had Jev check all 2,020 evidence items in the test Wiki without filtering. Evidence sufficiency rose from 26.7% to 100%, but median processing time grew from 1.511 s to 5.338 s, and every question required checking every item.

    Decision The existing search was discarding the right answer before any selection happened, so the gap could not be read only as a difference in selection ability on the same candidates. Checking every item per question also made call costs grow with the number of documents, which did not fit a service where users prepay for costs. So I decided to narrow candidates with search first and have Jev choose the evidence.

  3. Controlled comparison on 500 candidates: 87.50% coverage

    Problem Checking all evidence was too expensive to use in the service as is, the evaluation questions were concentrated on certain documents, and the questions even contained document titles. The existing search explored only some pages while Jev judged with all the evidence, so it was hard to tell whether the accuracy gap came from judgment or from how much each could see. I had to reduce candidates and also match the comparison conditions.

    Experiment and result I wrote 100 new questions from 9 papers (80 with answers, 20 without) and froze them before running. Both methods got the same 500 candidates and returned 8 results each for scoring. Evidence sufficiency came out at a sound 66.25% → 87.50%, but because candidates were processed sequentially, median processing time grew from 0.431 s to 9.090 s.

    Decision Even under the same conditions Jev picked evidence better, so I kept the structure where search gathers candidates and Jev makes the final evidence decision. Since these results came from public papers and questions I wrote, I did not treat them as general accuracy, and set reducing the wait added by sequential processing as the next task.

  4. 300 candidates and a parallelism comparison to reduce latency

    Problem Answers start only after evidence selection finishes, so processing time is the user's waiting time. A 9.090s median for 500 candidates processed sequentially was far too long against the previous 0.431s to be usable. Still, the higher accuracy was worth keeping, so I set out to cut the time.

    Experiment and result Candidate count affects cost and speed, so I cut candidates from the top 500 to 300 and processed up to 4 batches in parallel. Time dropped to 2.251 s, and questions where all needed evidence was picked rose from 70 to 73. The parallelism had been chosen without evidence, so I re-measured on the same 100 questions with only parallelism changed to 4, 6, 8 and 10. Median selection times were 2.066, 1.165, 0.945 and 0.886 s, and on the 42 questions whose selections changed, evidence sufficiency was 37, 38, 36 and 37, with no large difference.

    Decision Beyond 8-way parallelism the gain was only 0.06 s, and in production concurrent requests multiply as workers × parallelism, so I chose 8. At 1.137 s including candidate narrowing it is still slower than the old 0.431 s, but I held off on cutting candidates further because in that evaluation set some needed evidence ranked below 250. I accepted the longer processing time and adopted Jev, judging that delivering accurate evidence is the core of this service.

  5. Comparing candidate generators to find the limits of the production setting

    Problem However well Jev selects, it cannot use evidence that is not among the candidates. I needed to check how much of the right evidence the current candidate generation keeps.

    Experiment and result Reusing stored scores, I regenerated rankings for four candidate generators and compared how well each preserved the 97 pre-registered citation groups across the 80 answerable questions: BGE-M3 alone, the production hybrid (0.75 embedding + 0.25 normalized BM25), RRF, and an alternating union. At 100 candidates, the questions that preserved every citation were 74/80 for BGE-M3 alone, 63/80 for the production hybrid, 63/80 for RRF and 65/80 for the alternating union. MRR@500 over each citation’s best rank was 0.1811 for BGE-M3 alone against 0.1245 for the production hybrid, with median ranks of 19 and 40. Beyond 300 candidates the four converged to 79/80 and 78/80.

    Decision The production hybrid weighting ranks answer-bearing evidence lower than plain BGE-M3. At the 300 candidates used then the gap is small, so I left production unchanged and recorded it as the first condition to fix before cutting candidates further.

  6. Re-evaluating on a real-world set and improving evidence selection

    Problem I needed to check whether results from 9 papers held for what users actually upload, such as statutes, statistics and technical documents. Evaluation models also differed by feature, so results could not be stated on one basis.

    Experiment and result I wrote 100 questions from 11 public documents and reviewed them with my team. Every evaluation used gpt-6-luna, ran 3 times and was scored. With Jev off, answer accuracy was 71.7% and evidence relevance 70.0%; with it on, 93.0% and 95.4%. During evaluation I found a bug that double-counted request size and split candidate batches too finely. After the fix, on 20 questions × 3 runs, Jev calls dropped from 460 to 227 and input tokens from 7.13M to 5.25M, while evidence sufficiency rose from 94.1% to 100%. Comparing 300, 200, 150 and 100 candidates, evidence relevance was 95.0, 95.4, 95.0 and 95.0%, and recall of answer quotes was 0.873, 0.868, 0.849 and 0.808.

    Decision I chose 200, where recall held, cutting Jev cost (nearly proportional to candidates) by about a third. This reversed my earlier decision not to cut candidates further, based on the new set. In request routing, with few options, Jev and the LLM were close at 91.8% and 92.2%, so I now describe Jev's benefit there as response time (3.42s → 0.51s) rather than accuracy.

04 Results and lessons

Fixed evaluation set: 215/300 → 279/300 correct, 5.5 s average end-to-end response

I ran 100 questions that I wrote and reviewed with my team three times each, with Jev off and on. Answer accuracy rose from 71.7% to 93.0%, and the share where the selected evidence alone could produce the answer rose from 70.0% to 95.4%. Against plain RAG on the same questions, unsupported claims fell from 4.9% to 1.9%. The earlier adoption experiment (9 papers, coverage 66.25% → 91.25%) used a different set and grading, so it is not compared directly.

Scope and tradeoffs

Retrieval stays a fixed pipeline (semantic and keyword search plus Wiki graph traversal) that shows the answer, evidence, related pages and search path separately. I held off on a self-planning Query Agent because of cost and hallucination risk, and will add one when a question needs repeated planning and replanning; until then the fixed pipeline uses fewer calls and is easier to debug. Accuracy came at a cost in time and money. End-to-end responses average 5.5s, slower than plain RAG's 4.3s under the same conditions. Cost is about $2.7 per 1,000 requests against $0.19 to $0.35 with Jev off, estimated from actual tokens and unit prices. Correctly declining unanswerable questions was 57/60, below plain RAG's 60/60, so that is the next task. Retrieval gathers candidates and Jev decides, so the selector can be swapped.
