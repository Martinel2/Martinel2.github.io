Designing the agent execution environment: user-defined skills behind approval

Users repeat different tasks, so I let them define their own Skills. I judged that users can't trust AI that changes documents freely, so code checks permissions and scope, and changes apply only after approval. Code checks missed omitted requests, so drafts get a semantic evaluation and one rewrite at most.

PDF to Markdown, keeping tables and equations

Problem
When tables and equations in uploaded papers broke, the figures that answers rely on could not be used.
Judgment
I extracted body text with the fast AnyDoc and gave table and equation regions a separate path that reads them from the original.
Result

RAG that turns stored documents into knowledge: measuring and improving quality

Problem
Standard RAG, which picks the top 8 evidence passages, missed the expected evidence for 76 of 90 questions.
Judgment
I judged the bottleneck to be the embedding model failing to tell synonyms apart during selection.
Choice
Standard RAG now only filters evidence candidates, and the decision model Jev picks the final evidence.
Result
On 100 questions I reviewed myself, answer accuracy rose from 71.7% to 93.0%. Responses slowed from 0.23 s to 1.14 s, but I judged accuracy to be the core of the product and adopted Jev despite the slower response.

Per-request model routing: performance versus cost

Problem
Misrouting sent questions into document editing, and routing alone took 9 seconds.
Judgment
I replaced GPT-5-nano writing the conditions itself with Jev choosing from fixed options, and compared both on the same 98 requests.
Result
The old method got 77 of 98 right and Jev got 81. Median decision time fell from 8.967 s to 0.658 s, and the API cost for 100 questions from about $0.0891 to $0.0408.
Decision
Jev kept accuracy similar while cutting time and cost sharply, so I made it the routing model.

Agent Skills defined without code, with human-in-the-loop

Problem
Building every repeated task users wanted as a feature was impossible, and AI editing documents at will could frustrate users.
Judgment
Users define Skills in natural language without code, and code handles masking of sensitive data. For prompt injection, I referred to the published Claude system prompt so risky requests are refused, and code or instructions inside documents are read as plain text, never executed. Edits apply only after the user approves.
Result
I confirmed the answer that masked sensitive data cannot be read by the AI, the responses to prompt injection attempts, and that documents do not change before approval.

Finding the right number of Kubernetes workers

Problem
Running the AI pipeline that turns documents into a Wiki sequentially made later documents wait for external AI responses, and adding workers also increased API calls and memory.
Judgment
I split the work with Kafka, which can re-read messages and keeps order within a key, so AI jobs run asynchronously while duplicates are blocked by ID.
Result
Going from 1 to 4 workers cut analysis time from 282.11 s to 73.89 s. Concurrent AI requests inside a worker and embedding on the same GPU got slower the more I added, so I set separate scaling criteria per step.

LLM tracing and sensitive-data boundaries

Problem
When quality dropped, I could not see whether generation, evaluation or retry went wrong, and tracing could send user documents and personal data out.
Judgment
I made the quality loop visible step by step and kept the agent that touches user documents out of tracing.
Result
I rebuilt the evaluation loop as a LangGraph graph traced per node, disabled tracing for the agent graph and kept raw text out of saved state. Numeric personal data in prompt logs is masked.

Cancelling and recovering AI tasks

Problem
An AI task saves documents, folders, Wiki pages and Skills several times between model calls, so stopping execution left part of a cancelled task behind. Yet a run spanning the core DB, AI DB and object storage could not be wrapped in one long transaction.
Judgment
I decided to revert even committed changes. Asking the model for the reverse operation could not guarantee original values, approval scope or idempotency, and locking the whole service in one transaction could not survive long runs and failures across the model, HTTP and object storage, so I rejected both.
Result
In tests on real workers, with model calls set to fail during recovery, cancellation finished without calling the model or gateway once. Cancelling a task that organizes 2 folders and 6 documents at each of 9 points restored the original state, and a new worker continued recovery with the same idempotency key after a lost response.

Reframing a cost problem as data cleaning: 94% below the estimate

Problem
Rewriting 44,000 drug records into plain language with an LLM was estimated at about $200, over budget.
Judgment
Analysis of 100 source records showed about 70% duplication, so I treated each sentence as a block: sentences with the same meaning were marked as duplicates, keyed and removed, and the converted sentences were mapped back by key. Since real-time processing was unnecessary and the goal was saving cost, I converted every drug with the Batch API, 50% cheaper than the standard API.
Result
Data shrank from 1 GB to 326 MB, and processing estimated at $200 was completed for an actual $11.18.

An AI medication chatbot using personal health profiles

Problem
Users describe symptoms in different words from drug indications, which made search hard, and the health data needed for personalization could not go to external AI.
Judgment
Symptoms were too many and overlapping for a synonym dictionary, so I used semantic search; profile filtering had too many cases, so profile decisions stay in internal code. I chose Weaviate as lighter than Milvus, and Spring AI for orchestration because the backend was Spring, avoiding the load of a separate Python container.
Result
Users find drug information from natural-language symptoms, while pregnancy, current medications and underlying conditions are judged in internal code and left out of external LLM inputs.

A dietary supplement recommendation chatbot built from feedback

Problem
While running our exhibition booth, we were asked to add dietary supplements to the app. Unlike drug data, public supplement data was fragmented, and the same ingredient was sometimes named differently.
Judgment
Using AI, I hardcoded mappings that unify every supplement ingredient name in the data and normalized the fragmented data on that basis. I also used AI to express each benefit in varied wording and embedded it for search.
Result
When a user types “my eyes feel blurry”, the chatbot recommends only lutein supplements that are safe for that user.
