쌓인 문서를 지식으로 연결하는 RAG, 품질 측정과 개선

문제
상위 8개의 근거를 선택하는 일반 RAG 방식은 정해둔 정답 근거가 90문항 중 76문항이 누락됐습니다.
판단
선택 시에 임베딩 모델의 한계로 유의어를 가려내지 못하는 것을 병목으로 판단했습니다.
선택
일반 RAG 방식으로 근거 후보를 필터링만 하고, 의사결정 모델 Jev가 최종 근거를 고르도록 구성했습니다.
결과
직접 검수한 질문 100개로 평가한 결과, 정답률을 71.7%에서 93.0%로 높였습니다. 대신 응답은 0.23초에서 1.14초로 느려졌습니다. 하지만, 정확도가 제품의 핵심이라고 판단해 느려진 응답을 감수하더라도 Jev를 활용하는 방식을 채택했습니다.

요청별 모델 라우팅, 성능과 비용 트레이드오프

문제
라우팅이 틀려 질의가 문서 편집으로 넘어가는 오류가 존재했고, 라우팅에만 9초의 시간이 소요됐습니다.
판단
GPT-5-nano가 조건을 직접 작성하던 방식을, 정해 둔 선택지 중 Jev가 고르는 방식으로 바꿔 같은 요청 98개로 비교했습니다.
결과
기존 방식은 98개 중 77개, Jev는 81개를 맞혔습니다. 판단 시간 중앙값은 8.967초에서 0.658초로, 100문항 API 비용은 약 $0.0891에서 $0.0408로 줄었습니다.
결정
정확도는 비슷하게 유지하면서 시간과 비용을 크게 줄일 수 있어 Jev를 라우팅 모델로 사용하도록 결정했습니다.

코드 없이 정의하는 Agent Skill과 Human-In-The-Loop

문제
사용자가 요구하는 모든 반복 작업을 기능으로 만드는 것은 불가능했고, AI가 문서를 멋대로 수정하여 불편을 겪을 수 있었습니다.
판단
Skill은 사용자가 코드 없이 자연어로 정의하고, 민감정보 마스킹은 코드로 처리했습니다. Prompt Injection은 공개된 Claude System Prompt를 참고해 위험한 요청은 거절하고, 문서 속 코드나 지시문은 실행하지 않고 평문으로만 읽게 했습니다. 편집 반영은 사용자 승인 후에만 됩니다.
결과
민감정보가 마스킹되어 AI가 읽을 수 없다는 답변과 Prompt Injection 시도에 대한 응답을 확인했고, 승인 전에는 문서가 바뀌지 않는 것을 확인했습니다.

외부 Agent에 Fruition의 지식을 연결하고 권한을 위임한 MCP 설계

문제

판단
AI를 구독해 사용하는 사용자가 많음을 설문에서 확인해, MCP를 통해 구독 모델을 사용할 수 있도록 하고, 수수료를 받는 형태로 진행하면 모두 win-win하는 구조라 판단해 MCP를 설계 및 구현했습니다.
결과
Codex, Claude Code가 Fruition의 문서와 Wiki를 검색하고 편집 제안까지 하도록 연결했습니다. 연결마다 사용자, 워크스페이스, 허용 범위를 묶어, 연결을 끊으면 403으로 차단되는 것까지 확인했습니다.

문제
하드코딩된 AI 모델 문제를 고치다가, 비슷하게 검토해야 할 부분을 Claude에게 모두 찾게 하니 저장소 5개에서 고치는 방법이 여러 가지인 문제가 수십 개 나왔습니다.
판단
트레이드오프 정리와 구현은 에이전트가 하고, 판단 및 결정은 제가 직접 했습니다. 멀티 에이전트 구조로 수정한 코드를 바로 검증하도록 했고, 검증은 새 세션에서 계획서 기준 일치/불일치만 판정하게 했습니다.
결과
3일 동안 PR 78개를 올렸고, 모두 반영되었습니다.

적절한 Kubernetes Worker 수 측정

문제
문서를 Wiki로 만드는 AI 파이프라인을 순차 처리하면 뒤의 문서가 외부 AI 응답을 기다려야 했고, 작업자를 늘리면 API 호출과 메모리도 함께 늘었습니다.
판단
메시지를 다시 읽을 수 있고 같은 키 안에서 순서를 보장하는 Kafka로 작업을 나눠, AI 작업을 비동기로 돌리면서 ID 기준으로 중복 처리를 막았습니다.
결과
Worker를 1개에서 4개로 늘려 분석 시간을 282.11초에서 73.89초로 줄였습니다. 반면 Worker 안의 동시 AI 요청과 같은 GPU의 벡터 생성은 늘릴수록 오히려 느려져, 단계별로 확장 기준을 나눴습니다.

AI 작업 취소와 복구

문제
AI 작업은 모델 호출 사이사이에 문서, 폴더, Wiki, Skill을 여러 번 저장합니다. 그래서 실행만 멈추면 취소한 작업의 일부가 그대로 남았습니다. 하지만 core DB, AI DB, 객체 저장소에 걸친 실행을 긴 트랜잭션 하나로 묶을 수도 없었습니다.
판단
이미 커밋한 변경까지 되돌리기로 했습니다. 모델에게 반대 작업을 시키면 원래 값과 승인 범위, 멱등성을 보장할 수 없었습니다. 또한 서비스 전체를 트랜잭션 하나로 잠그면 모델, HTTP, 객체 저장소의 긴 실행과 장애를 버틸 수 없어 두 방법 모두 기각했습니다.
결과
실제 worker로 돌리는 테스트에서 복구 중 모델을 부르면 실패하게 해 두고, 모델과 게이트웨이를 한 번도 부르지 않고 취소가 끝나는 걸 확인했습니다. 폴더 2개와 문서 6개를 정리하는 작업을 9개 지점 각각에서 취소해도 원래 상태로 돌아왔고, 응답이 유실된 뒤 새 worker가 같은 멱등키로 복구를 이어 가는 것도 확인했습니다.
