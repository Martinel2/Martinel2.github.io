RAG 과정의 검색 정확도 개선

저장된 문서에서 AI 답변에 필요한 근거를 찾고, 답이 없는 질문에는 근거를 붙이지 않게 하는 기능입니다.

  • 답변 근거 선택 개선 문제: 문서 근거로 답하는 서비스에서 기존 검색이 근거를 놓치거나 답 없는 질문에도 근거를 붙여 답변 신뢰도가 흔들림. 판단: GPT 선택은 비용(약 2.5배)·시간 부담, 가중치·RRF 조정은 여러 값을 실험해도 점수가 비슷해, 선택지 안에서만 판단하는 Jev 채택. 해결: BGE-M3·BM25로 후보를 모으고 Jev가 최종 근거를 고르는 2단계 구조. 동일 후보·블라인드 교차 채점으로 비교한 뒤 후보 300개·4병렬로 조정. 성과: 답이 있는 80문항의 근거 충족률 66.25% → 91.25%. 선택 시간 중앙값 9.090초 → 2.251초(기존 0.431초보다 느림).

에이전트 실행 환경 - Skill·승인·라우팅과 대화 맥락

반복 작업을 Skill로 저장·재사용하고 실제 변경은 사용자 승인 후 반영하도록 설계했습니다. 요청 분류에는 Jev를 적용했고, 모델에 보낼 대화 맥락과 편집 입력의 범위도 함께 정했습니다.

  • 사용자 정의 작업 지침(Skill) 문제: 사용자마다 반복 작업이 달라 모두 기능으로 만들 수 없고, AI 편집안이 요청을 빠뜨린 채 전달돼 같은 결과를 원하는 작업을 운에 맡기게 됨. 판단: 지침은 AI, 권한·실행 범위 검사는 코드, 게시와 실제 반영은 사용자가 맡도록 책임 분리. 해결: 자연어 지침 작성·검토·게시와 권한·승인 우회 검사, 미리보기 후 별도 승인. 편집 결과는 의미 평가 후 최대 1회 재작성. 성과: 편집 품질 94 → 104/114건(82.5% → 91.2%). 승인 전에는 문서가 바뀌지 않음을 확인.
  • Jev 기반 요청 분류 개선 문제: 질문을 편집으로 분류하는 등 잘못된 작업으로 이어져 서비스 신뢰성에 직결. 판단: 정해진 선택지 안에서 고르는 Jev가 분류에 맞다고 보고, 출시 직후 모델이라 위험이 작은 요청 분류에서 먼저 검증. 해결: 작업 종류와 부가 조건을 고르는 라우팅에 Jev를 적용하고, 같은 요청 98개로 기존 방식·GPT-5-nano와 비교. 성과: 작업 종류·조건 정답 77 → 81건(GPT-5-nano 63건), 판단 시간 중앙값 8.967초 → 0.658초.
  • 대화 메모리와 편집 입력 범위 문제: 대화와 문서를 통째로 모델에 보내면 비용과 지연이 커짐. 해결: 최근 메시지 6개 외에는 누적 요약으로 압축하고, 편집은 대상 줄과 주변 문맥만 전달해 1,000줄 문서 입력을 원문의 5.58%로 줄임.

실행 신뢰성과 LLM 추적

AI가 이미 저장한 변경을 되돌리고, 실행 과정을 단계 단위로 확인할 수 있게 하는 작업입니다. 여러 저장소에 걸친 실행을 하나의 트랜잭션으로 묶을 수 없어 역작업으로 복구했습니다.

  • 취소한 작업의 역순 복구 문제: AI 작업이 모델 호출 사이에 문서·폴더·Wiki·Skill을 여러 번 저장해, 실행만 멈추면 일부 변경이 남음. 해결: 취소 상태를 먼저 저장해 후속 쓰기를 막고, 변경 전 snapshot과 승인에 연결된 멱등키로 자식부터 역순 복구. 복구는 모델 호출 없이 실행 기록만 쓰고, 전체 복구를 확인해야 취소가 확정.
  • 다른 작업의 기여를 지우지 않는 복구 문제: 개념 페이지가 여러 문서의 기여를 합친 결과라, 과거 snapshot으로 덮으면 다른 문서의 정상 기여까지 사라짐. 해결: 작업·revision·문서별 기여를 덧붙이기만 하는 이력으로 남기고 복구 시 대상 기여만 제외해 재조립.
  • LLM 실행 추적과 민감정보 경계 문제: 평가 루프가 일반 Python 흐름이라 단계별로 볼 수 없고, 추적에 보내는 내용에 민감정보가 섞일 수 있었음. 해결: 평가 루프를 LangGraph 그래프로 재구성해 생성·평가·재시도를 노드 단위로 추적. Agent 그래프는 추적을 끄고 도구 조회 원문을 상태 저장에서 제외하며, 자체 프롬프트 로그는 기록 전 숫자 개인정보를 마스킹.

문서 확장자 변환 파이프라인 구축과 Wiki 생성 시간 개선

사용자가 올린 PDF를 검색과 답변에 활용하도록 변환하고, 여러 문서의 Wiki 생성 시간을 줄였습니다.

  • PDF → Markdown 변환 문제: 논문 PDF의 표·수식이 깨지면 Wiki와 답변의 근거가 되는 수치를 쓸 수 없음. 판단: 깨진 곳만 고치는 방식은 탐지가 오류를 놓쳤고, 전체 AI 변환은 표·수식 정확도와 비용이 부족해 내용 유형별 처리로 전환. 본문은 추출이 빠른 AnyDoc, 복원은 GPU 운영비가 드는 sLLM 대신 상용 LLM API. 해결: 본문은 AnyDoc으로 추출해 깨진 부분만 AI로 보완, 표·수식은 원본 영역을 따로 판독, 그림은 원본 보존. 성과: 같은 30쪽·445단위 블라인드 평가에서 통과율 45.17% → 89.89%.
  • 문서의 Wiki 생성 병렬화 문제: 문서를 하나씩 처리해 대형 문서일수록 Wiki 생성 대기가 길어짐. 판단: Worker 수·동시 요청·GPU 병렬을 각각 비교. 외부 AI 응답 대기에는 Worker 증설이 효과적이었고, 동시 요청과 GPU 병렬은 오히려 느려져 제외. 메모리 약 4배 증가는 EKS 분산 배치로 감수. 해결: Kafka로 문서별 작업을 나눠 Worker 최대 4개로 처리. 성과: 문서 4개 분석 시간 282.11초 → 73.89초(약 74% 단축).

MSA: 기능별로만 나누면 DB 부하는 그대로이고 서비스 간 호출만 늘어난다고 보고 데이터 소유권 기준 분리를 제안, 팀원·멘토와 경계·통신 방식을 공동 설계.

데이터 정제 파이프라인 구축

약 4만 4천 건의 의약품 원문을 쉬운 설명으로 바꾸는 작업입니다. 같은 문장은 한 번만 변환해 약품별로 재사용했습니다.

  • 문제: 약 4만 4천 건을 그대로 쉬운 설명으로 바꾸면 API 비용이 약 $200으로, 예산 안에서 모든 약의 설명을 제공할 수 없었음. 판단: 약 수를 줄이는 대신 같은 문장은 한 번만 변환. 실시간 응답이 필요 없는 작업이라 Batch API로 대기 시간을 받아들이고 비용을 낮춤. 해결: 문장 블록으로 나눠 완전 일치 문장을 통합하고 GPT Batch API로 변환한 뒤 약품별로 재연결. 2026년 PySpark로 재현해 단계별 효과 측정.

    성과: 전체 원문 변환 예상 비용 약 $200 대비 실제 API 지출 $11.18. 재현 실험에서 완전 일치 중복 제거로 텍스트 744MB → 44.1MB(−94.1%).

    비용은 예상치와 실지출의 비교이며 전처리 인건비는 제외했습니다.

개인 건강 정보 기반 답변 제공 AI 복약 챗봇 개발

사용자가 증상을 자연어로 물으면 관련 약품과 복약 정보를 찾는 기능입니다. 건강 프로필은 내부에서 판단해 개인화에 활용하고, 외부 AI에 보내는 정보와 분리했습니다.

  • 문제: 약을 먹어도 되는지 확인하려는 사용자의 증상 표현과 약 효능 용어가 달라 검색이 어렵고, 개인화에 필요한 건강 정보는 외부 AI로 보낼 수 없었음. 판단: 동의어 사전은 증상이 많고 서로 겹쳐 의미 검색으로, 프로필 필터링은 걸러야 할 경우가 너무 많아 내부 판단으로 전환. 해결: Weaviate 의미 검색과 AI 오케스트레이션으로 약품 탐색·복약 위험·섭취량별 처리 경로 구성. 임신 여부·복용약·기저질환은 내부 코드로 판단. 성과: 자연어 증상으로 약품 정보를 탐색하고, 해당 건강 프로필을 외부 LLM 입력에서 제외한 개인화 흐름 구현.

백엔드 기능 구현

앱에서 약품을 찾고 복약 위험정보를 확인하며, 복약 알림·기록과 가족 프로필을 사용할 수 있도록 서버 기능을 구현했습니다. 모바일 앱과 사용자·보안 기능을 맡은 팀원과 연동했습니다.

  • Java·Spring Boot 기반 의약품 DB 설계, 검색·자동완성과 복약 위험정보(DUR) 표출 구현. 부분 일치·자동완성은 Elasticsearch로, 반복되는 위험정보 조회는 Redis 캐시로 처리해 검색 응답 5~7초 → 평균 0.8초.
  • FCM 복약 알림·로그, 딥링크 친구 초대, 가족 프로필 전환을 구현하고, Notion에 API 문서·회의록·ADR을 남겨 의사결정을 공유했습니다.

전시 현장 피드백을 반영한 기능 확장

부산대학교 대표 전시팀으로 두 차례 부스를 운영하며 방문자 100명 이상에게 시연하고 피드백 10건을 받았습니다. 대부분이 건강기능식품 요청이어서 보유한 데이터 범위에서 기능으로 연결했습니다.

  • 건강기능식품 지원 확대 문제: 첫 전시에서 의약품만 확인할 수 있어, 건강기능식품도 함께 보고 싶다는 요청을 받음. 해결: 보유한 건강기능식품 데이터 범위에서 검색·자동완성 대상에 추가하고, 복용 주의·병용 정보 표출, 복약 알림·기록 등록, 챗봇 답변 대상까지 확장. 성과: 전시에서 받은 요청을 다음 개발 범위로 연결. 확보한 데이터에 한정되며 의약품과 같은 전수 정보는 아님.

문제 해결 과정과 실험 결과는 상세 포트폴리오에서 볼 수 있습니다.
