01 문제 상황

핵심 타겟층인 대학원생들이 주로 활용하는 논문은 PDF로 제공됐습니다. PDF를 지식으로 활용하기 위해 Markdown으로 변환하는 오픈소스를 사용해봤으나, 표의 행·열 관계와 수식이 손상됐습니다.

02 실험과 개선 과정

  1. 오픈소스로 변환 시 손상된 부분만 복원하려했지만, 탐지에서 오류를 놓쳤습니다

    AI가 복원한 96개 중 85개는 평가를 통과했습니다. 하지만 복원하지 않은 부분을 확인하자 오류·누락이 107개 남아 있었습니다. OCR 대조를 추가한 별도 실험에서는 통과율을 80.00%에서 97.53%로 높였지만, 정상인 내용 50개도 수정 대상으로 골랐고 처리 단계의 시간 합은 약 12분 35초였습니다.

    판단 무엇을 복원할지 고르는 과정에서 오류를 놓치고, 이를 보완하는 검사에도 비용이 들었습니다. 손상 탐지에 의존하게되고, 그에 따른 비용이 드니 원본 페이지 전체를 AI가 읽게 하는게 더 나을 수도 있겠다고 판단했습니다.

  2. 전체 페이지를 AI가 읽어도 표와 수식 오류가 남았고, 비용이 부담되었습니다

    논문 PDF 25개(415쪽)를 전체 AI로 처리했을 때 내용 보존 통과율은 91.92%였습니다. 하지만 표·수식의 값과 구조가 모두 맞은 비율은 58.84%였고, 모든 페이지를 처리하는 호출 부담도 컸습니다.

    판단 모든 내용을 같은 방식으로 AI에 맡기기보다, 본문은 필요한 부분에만 AI를 쓰고 표·수식은 각각의 구조를 보존할 수 있는 입력을 제공해야겠다고 판단했습니다. 본문과 표, 수식의 처리 경로를 나누고, 본문을 빠르게 추출하면서 필요한 부분만 AI로 복원할 방법을 모색했습니다.

  3. AnyDoc을 비교해보고, 본문 추출에 적용했습니다

    Threads에서 PDF 변환 도구 AnyDoc을 알게 됐고, GitHub의 Docling 대비 평가 결과를 보고 기존 실험에 쓰던 PDF 4개(30쪽)로 비교했습니다. 기존 Docling 처리 기록은 134.19초였고, AnyDoc의 텍스트 추출은 1.68초로 약 80배 짧았습니다. Docling은 OCR과 표 분석까지 포함한 시간이었지만, 이를 감안해도 빠르다고 생각했습니다. AnyDoc 결과에서는 한 문서의 글자가 깨졌고, PDF 내부에 글자 코드를 실제 문자로 연결하는 정보가 빠진 것이 원인이었습니다.

    판단 처리 범위가 달라 전체 변환이 80배 빨라졌다고 볼 수는 없지만, 본문을 빠르게 추출하는 데 활용할 가치가 있다고 판단했습니다. 표와 수식은 이미 별도로 복원하고 있었으므로 그 과정은 유지하고, 본문 추출을 AnyDoc으로 바꾸되 글자가 깨진 페이지는 AI로 보완하기로 했습니다. 읽는 순서가 섞인 페이지도 AI로 복원하고, 그림은 원본을 보존했습니다.

01 문제 상황

사용자 요청을 잘못 분류하거나, 검색한 자료에서 답변에 필요한 근거를 놓치는 문제가 있었습니다. 먼저 요청을 실행 가능한 작업 중 하나로 분류하는 데 Jev를 시험했고, 이후 검색 결과에서 답변 근거를 고르는 데 적용했습니다. 기존 RAG는 답이 있는 질문 80개 중 53개만 필요한 근거를 모두 골랐고, 답이 없는 질문 20개에도 모두 근거를 반환했습니다.

02 실험과 개선 과정

  1. 요청 분류에서 정확도와 판단 시간이 개선돼 RAG로 적용을 넓혔습니다

    9/14일 출시된 선택형 판단 모델 Jev의 원리와 자체 평가 성능을 보고 라우팅 성능 향상에 도움이 될 것이라 판단했습니다. 이에 사용자 요청을 질문, 문서 편집, 문서 생성, 폴더 정리 등으로 나누는 라우팅에 적용했습니다. 모델이 판단한 98개 요청에서 작업 종류와 부가 조건을 모두 맞힌 수는 기존 JSON 방식 77개, 같은 선택지를 받은 GPT-5-nano 63개, Jev 81개였습니다. 판단시간 중앙값 또한 기존 8.967초에서 Jev 0.658초로 개선된 결과를 보였습니다.

    판단 Jev는 정확도와 속도 모두 가능성을 보였습니다. 이 결과를 바탕으로, 기존 검색에서 해결하지 못한 답변 근거 선택에도 Jev를 적용해보기로 했습니다.

  2. 검색 가중치 조정으로 남은 한계를 Jev의 근거 선택으로 개선했습니다

    질문 원문을 검색에 사용하고 의미 점수의 비중을 높여, 질문 110개에서 정답 자료가 첫 번째에 나오는 경우를 50개에서 57개로 향상시켰습니다. 하지만 이는 일부 편향된 실험이였으며, 새로운 질문에서도 필요한 근거를 안정적으로 고르는 문제는 해결하지 못했습니다. 이에 라우팅에서 효과를 확인한 Jev를 근거 선택에 적용했습니다. 같은 검색 후보로 비교하자 답이 있는 80개 질문 중 필요한 근거를 모두 고른 경우가 기존 53개에서 Jev 70개로 증가했습니다. 답이 없는 질문에 근거를 반환한 경우도 20건에서 1건으로 감소했습니다.

    판단 해당 테스트 계정에 존재하는 모든 근거를 보고 판단하도록 하는 방식이기 때문에 질의 한 번 수행시마다 같은 과정을 반복하기엔 시간과 비용이 부담되었습니다. 질문과 비슷한 자료를 찾는 단계와, 그 자료가 실제 답을 뒷받침하는지 판단하는 단계를 나눌 필요가 있겠다고 판단하여 기존 하이브리드 검색으로 후보를 추린 뒤 Jev가 질문과 대조해 근거를 다시 고르는 방법을 고려했습니다.

  3. 증가한 처리 시간을 줄이기 위한 병렬 배치 처리 적용

    후보를 최대 500개까지 순서대로 처리했을 때 준비와 선택 시간의 중앙값은 9.090초로, 기존 방식의 0.431초보다 느려졌습니다. 빠른 처리를 위해 후보를 상위 300개로 줄이고 최대 4개 묶음을 병렬 처리해 시간은 2.251초로 줄었고, 필요한 근거를 모두 고른 질문은 70개에서 73개로 늘었습니다.

    판단 시간을 줄였음에도 2.251초로 기존 0.431초보다는 느렸습니다. 후보를 더 줄이고 더 많은 묶음의 병렬 처리 시도를 고려해봤으나, 필요한 근거가 250위보다 아래에 존재하는 사례가 있어 해당 안은 기각했습니다. 비록 처리 시간이 늘었지만, 정확도가 서비스의 핵심이라고 판단하여 Jev를 채택하기로 결정했습니다.

02 실험과 개선 과정

  1. 문서 처리 시간이 느려 Worker를 늘려 응답 대기를 겹쳤습니다

    같은 문서 4개를 처리하는 Worker를 1개에서 4개로 늘리자 분석 시간이 282.11초에서 73.89초로 줄었습니다. 대신 프로세스 메모리 합은 약 352MiB에서 1,401MiB로 늘었습니다.

    판단 외부 API를 기다리는 동안 다른 문서를 처리하면 이득이 있었지만, Worker 수만큼 자원 부담도 커졌습니다. 시간만 보고 운영 설정을 늘리지는 않았습니다. Worker 수와 문서 내부의 동시 요청 수를 나눠 확인했습니다. 같은 작업공간에 저장하는 요청은 잠금으로 대기하고, 다른 작업공간은 병렬 진행하는지도 점검했습니다. 메모리를 약 4배 더 사용하지만, MSA형태로 EKS를 사용해 AI 기능이 제공되므로, 분산이 가능할 것이라 판단해 문서 병렬 처리 시 최대 Worker 4개 사용을 채택했습니다.

  2. 동시 요청을 더 늘리자 오히려 느려졌습니다.

    Worker 4개에서 각 Worker의 동시 AI 요청을 2개에서 4개로 늘리자 73.89초에서 95.92초로 느려졌습니다. 같은 GPU에서 벡터 생성 프로세스를 2개 실행했을 때도 각각의 처리시간이 약 9.5초에서 19~21초로 늘었습니다.

    판단 외부 응답을 기다리는 분석과 같은 장치를 나눠 쓰는 벡터 생성은 병렬화 효과가 달랐습니다. 동시성을 높이면 항상 빨라질 것이라 생각했지만, 맞지 않았습니다. 따라서 해당 안은 적용 시 아무런 메리트가 없다고 판단해 기각했습니다.

02 실험과 개선 과정

  1. 반복하는 문서 작업을 사용자가 직접 정의하도록 확장했습니다

    회의록 정리처럼 사용자마다 반복하는 작업을 모두 개발자가 추가하는 데는 한계가 있었습니다. 사용자가 자연어로 작업을 설명하면 AI가 재사용할 Markdown 작업 지침인 Skill로 구체화하고, 사용자가 검토한 뒤 게시하도록 만들었습니다.

    판단 Skill은 Agent가 이후에도 반복해서 읽는 지침이므로 일반 채팅보다 오래 영향을 줍니다. AI가 만든 초안은 바로 저장하지 않고 제안으로만 보여주며, 사용자가 최종 게시할 때 Skill과 버전을 저장하도록 했습니다.

  2. 사용자가 작성한 지침과 AI의 안전 판단을 모두 검증했습니다

    승인 우회나 권한 무시는 규칙으로 차단할 수 있었지만, 같은 의도를 다르게 표현하면 정규표현식만으로는 잡기 어려웠습니다. 참고 문서에도 위험한 지시가 들어갈 수 있었고, 사용자는 검토를 통과한 초안을 게시 전에 다시 수정할 수 있었습니다.

    판단 명확한 위험은 코드로, 우회 표현은 LLM으로 검사했습니다. 모델이 지적한 위험 문구가 실제 입력에 있는지도 서버에서 확인했습니다. 참고 문서는 권한과 원문을 검사하되 모델에는 필요한 문서 구조만 전달했고, 최종 게시할 내용은 다시 검사했습니다. 위험 문구를 몰래 고치지 않고 위치와 이유를 보여주며, 사용자가 재생성을 선택한 경우에만 제거하도록 했습니다.

  3. 작업 지침의 게시와 실제 문서 변경을 각각 사용자 승인에 연결했습니다

    지침을 안전하게 게시했더라도 실행할 때 어떤 문서가 바뀌는지는 별도로 확인해야 했습니다. 편집은 수정 전후 차이를, 폴더 정리는 만들 폴더와 이동할 문서를 구체적인 계획으로 보여주도록 했습니다.

    판단 작업 분류는 라우터가 맡고 실행기는 정해진 작업을 수행하도록 역할을 분리했습니다. 출력 형식과 수정 범위는 코드로 검사하고, 사용자가 결과를 확인해 승인한 뒤에만 반영했습니다. 문서 6개의 폴더 정리 실행에서는 승인 전 변경 없이, 승인 후 주제별 폴더 3개를 만들고 문서를 옮기는 흐름을 확인했습니다.

증상과 약품 효능은 같은 뜻이어도 다른 단어로 표현됩니다. 동시에 개인화에는 임신 여부·복용약·기저질환이 필요했지만, 이 프로필까지 외부 LLM에 전달하면 민감정보의 사용 범위가 넓어집니다.

02 설계와 구현 과정

  1. 증상 표현과 약품 설명이 달라도 연결할 필요가 있었습니다

    사용자가 말하는 증상과 약품 효능에 적힌 단어는 같은 뜻이어도 다를 수 있었습니다. 개인화에는 임신 여부·복용약·기저질환도 필요했습니다.

    판단 자연어 표현을 연결하는 일과 건강 프로필의 조건을 판단하는 일은 구분할 수 있었습니다. 둘을 모두 외부 AI에 맡기면 필요 이상의 프로필 정보까지 전달하게 됩니다. 약품 효능을 Weaviate에 저장해 증상과 의미가 가까운 정보를 찾도록 했습니다. 질문에 따라 약품 탐색·복약 위험·섭취량 정보를 처리하는 경로도 나눴습니다.

  2. 건강 프로필은 내부 코드에서 판단하도록 분리했습니다

    임신 여부·복용약·기저질환을 이용한 개인화가 필요했지만, 이 필드들을 외부 LLM 입력에 함께 넣을 필요는 없었습니다.

    판단 증상 표현을 이해하는 데 AI를 활용하되, 프로필을 사용하는 판단은 입력과 규칙을 직접 관리할 수 있는 내부 코드에 두기로 했습니다. 해당 프로필 필드는 외부 LLM 입력에서 제외하고, 내부 판단을 증상 검색 결과와 연결해 개인화 정보를 제공하도록 구현했습니다.

04 결과와 배운 점

증상은 의미로 찾고, 건강 프로필은 내부에서 판단

자연어 증상으로 약품 정보를 탐색하면서도 임신 여부·복용약·기저질환 필드는 외부 LLM 입력에서 제외했습니다. AI에 전달할 정보와 내부 코드가 판단할 정보를 구분한 구현 경험입니다.

결과의 범위 · 트레이드오프

프로필 조건이 바뀌면 내부 코드도 수정해야 합니다. 특정 프로필 필드를 입력에서 제외한 것이며, 의약 판단 정확도나 모든 경로의 정보 유출 차단율을 측정한 결과는 아닙니다.
