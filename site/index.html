2026.07 — 2026.09

PDF 변환 오픈 소스 : AnyDoc, DoclingLLM APIPythonLLM-as-a-Judge

01 문제 상황

핵심 타겟층인 대학원생들이 주로 활용하는 논문은 PDF로 제공됐습니다. PDF를 지식으로 활용하기 위해 Markdown으로 변환하는 오픈소스를 사용해봤으나, 표의 행·열 관계와 수식이 손상됐습니다.

02 실험과 개선 과정

  1. 오픈소스로 변환 시 손상된 부분만 복원하려했지만, 탐지에서 오류를 놓쳤습니다

    AI가 복원한 96개 중 85개는 평가를 통과했습니다. 하지만 복원하지 않은 부분을 확인하자 오류·누락이 107개 남아 있었습니다. OCR 대조를 추가한 별도 실험에서는 통과율을 80.00%에서 97.53%로 높였지만, 정상인 내용 50개도 수정 대상으로 골랐고 처리 단계의 시간 합은 약 12분 35초였습니다.

    판단 무엇을 복원할지 고르는 과정에서 오류를 놓치고, 이를 보완하는 검사에도 비용이 들었습니다. 손상 탐지에 의존하게되고, 그에 따른 비용이 드니 원본 페이지 전체를 AI가 읽게 하는게 더 나을 수도 있겠다고 판단했습니다.

  2. 전체 페이지를 AI가 읽어도 표와 수식 오류가 남았고, 비용이 부담되었습니다

    논문 PDF 25개(415쪽)를 전체 AI로 처리했을 때 내용 보존 통과율은 91.92%였습니다. 하지만 표·수식의 값과 구조가 모두 맞은 비율은 58.84%였고, 모든 페이지를 처리하는 호출 부담도 컸습니다.

    판단 모든 내용을 같은 방식으로 AI에 맡기기보다, 본문은 필요한 부분에만 AI를 쓰고 표·수식은 각각의 구조를 보존할 수 있는 입력을 제공해야겠다고 판단했습니다. 본문과 표, 수식의 처리 경로를 나누고, 본문을 빠르게 추출하면서 필요한 부분만 AI로 복원할 방법을 모색했습니다. 표·수식은 해당 부분의 원본 이미지를 AI에 함께 제공했습니다. 수식이 잘못 복원된 사례를 확인하니, 잘라낸 이미지에 이웃 수식까지 포함돼 있었습니다. 모델과 프롬프트는 그대로 두고 이미지 경계만 바로잡자 두 수식이 모두 정확하게 복원됐습니다.

  3. AnyDoc을 비교해보고, 본문 추출에 적용했습니다

    Threads에서 PDF 변환 도구 AnyDoc을 알게 됐고, GitHub의 Docling 대비 평가 결과를 보고 기존 실험에 쓰던 PDF 4개(30쪽)로 비교했습니다. 기존 Docling 처리 기록은 134.19초였고, AnyDoc의 텍스트 추출은 1.68초로 약 80배 짧았습니다. Docling은 OCR과 표 분석까지 포함한 시간이었지만, 이를 감안해도 빠르다고 생각했습니다. AnyDoc 결과에서는 한 문서의 글자가 깨졌고, PDF 내부에 글자 코드를 실제 문자로 연결하는 정보가 빠진 것이 원인이었습니다.

    판단 처리 범위가 달라 전체 변환이 80배 빨라졌다고 볼 수는 없지만, 본문을 빠르게 추출하는 데 활용할 가치가 있다고 판단했습니다. 표와 수식은 이미 별도로 복원하고 있었으므로 그 과정은 유지하고, 본문 추출을 AnyDoc으로 바꾸되 글자가 깨진 페이지는 AI로 보완하기로 했습니다. 읽는 순서가 섞인 페이지도 AI로 복원하고, 그림은 원본을 보존했습니다.

01 문제 상황

기존 검색은 관련 자료를 찾아도 답변에 필요한 사실을 모두 담지 못했습니다. 답이 있는 질문 80개 중 53개만 필요한 근거 탐색에 성공했고, 문서에 답이 없는 질문 20개에도 모두 근거를 반환했습니다.

02 실험과 개선 과정

  1. 하이브리드 검색의 가중치를 변경하여도 안정적인 성능이 나오지 않아 판단 모델 Jev 고려

    하이브리드 검색의 가중치를 변경해보아도, 그 실험에 편향되어 점수가 높아졌습니다. 이에 범용적으로 알맞은 근거를 선택하여 정확도를 높이고자 했습니다. 이때, 선택형 판단 모델 Jev가 9/14일에 공개되어, 제공받은 무료 크레딧으로 실험을 진행했습니다. 같은 검색 후보를 주고 비교하자 기존 방식은 80개 질문 중 53개, Jev는 70개에서 필요한 근거를 모두 골랐습니다. 답이 없는 질문에 근거를 반환한 경우도 20건에서 1건으로 줄었습니다.

    판단 해당 테스트 계정에 존재하는 모든 근거를 보고 판단하도록 하여, 질의 한 번 수행시마다 같은 과정을 반복하기엔 시간과 비용이 부담되었습니다. 질문과 비슷한 자료를 찾는 단계와, 그 자료가 실제 답을 뒷받침하는지 판단하는 단계를 나눌 필요가 있었습니다. 기존 하이브리드 검색으로 후보를 추린 뒤 Jev가 질문과 대조해 근거를 다시 고르게 했습니다. 품질 개선과 함께 추가 호출에 드는 시간도 확인했습니다.

  2. 증가한 처리 시간을 줄이기 위한 병렬 배치 처리 적용

    후보를 최대 500개까지 순서대로 처리했을 때 준비와 선택 시간의 중앙값은 9.090초로, 기존 방식의 0.431초보다 느려졌습니다. 빠른 처리를 위해 후보를 상위 300개로 줄이고 최대 4개 묶음을 병렬 처리해 시간은 2.251초로 줄었고, 필요한 근거를 모두 고른 질문은 70개에서 73개로 늘었습니다.

    판단 시간을 줄였음에도 2.251초로 기존 0.431초보다는 느렸습니다. 후보를 더 줄이고 더 많은 묶음의 병렬 처리 시도를 고려해봤으나, 필요한 근거가 250위보다 아래에 존재하는 사례가 있어 기각했습니다. 시간이 늘었지만, 정확도가 서비스의 핵심이라고 판단하여 Jev를 채택하기로 결정했습니다.

KafkaPostgreSQLBGE-M3동시성·메모리

01 문제 상황

문서를 순차 분석하면 뒤의 문서가 외부 AI 응답을 기다려야 했습니다. 작업자를 늘리면 API 호출과 메모리 사용도 함께 증가하므로 어느 단계까지 확장할지 확인해야 했습니다.

02 실험과 개선 과정

  2. 다시 비교하자 품질은 비슷했고 속도에서 차이가 났습니다

    한 건씩 비교한 정답은 기존 모델 71개, Jev 72개였습니다. 큰 품질 차이는 유지되지 않았지만 판단시간 중앙값은 8.162초에서 0.254초로 줄었고, 실제 문서 질문 12개는 모두 맞혔습니다.

    판단 Jev가 더 정확하다고 주장하기보다 비슷한 품질에서 시간을 줄일 후보로 봤습니다. 다른 근거 연결 작업에서는 빨라져도 비용이 늘어, 모든 판단을 같은 모델로 바꾸는 것은 적절하지 않았습니다. 문서 처리 단계도 따로 측정해 한 단계의 개선을 전체 처리시간 단축으로 해석하지 않았습니다. 실제 오병합과 저장·검색 영향을 더 확인할 대체 후보로 정리했습니다.

02 문제 분석과 구현 과정

  1. 비용을 줄이기 전에 반복해서 보내는 내용을 확인했습니다

    약 4만 4천 건의 약품 원문을 모두 변환하면 API 비용이 약 $200으로 예상됐습니다. 100개 표본을 살펴보니 약 70%가 중복되는 내용이었습니다.

    판단 약품 수를 줄이면 사용자가 얻는 설명도 줄어듭니다. 같은 문장을 약품마다 반복 변환하는 낭비부터 줄이면 기능 범위를 유지할 수 있다고 판단했습니다. 표본 분석과 작업 계획으로 팀을 설득해 전처리 기간 7일을 확보했습니다. 원문을 문장 블록으로 나누고, 문자열이 완전히 같지 않은 유사 표현도 어미 정리와 유사도 비교로 묶었습니다.

  2. 한 번 변환한 설명을 여러 약품에 다시 연결했습니다

    중복을 정리하자 변환 대상이 1GB에서 326MB로 줄었습니다. 다만 문장을 합치는 과정에서 약품별 연결이나 숫자가 달라지면 잘못된 설명이 될 수 있었습니다.

    판단 중복 제거 자체보다 각 약품에 올바른 설명을 돌려주는 것이 중요했습니다. 서비스 중 즉시 응답하는 작업이 아니므로 일괄 처리의 대기 시간도 허용할 수 있었습니다. 약품 ID와 문장 블록 ID의 연결을 보존하고, 용량과 숫자는 따로 처리해 표본을 직접 확인했습니다. 고유 문장만 GPT Batch API로 변환한 뒤 각 약품에 다시 연결했습니다.

2025.03 — 2025.12

JavaSpring BootSpring AIWeaviate

01 문제 상황

증상과 약품 효능은 같은 뜻이어도 다른 단어로 표현됩니다. 동시에 개인화에는 임신 여부·복용약·기저질환이 필요했지만, 이 프로필까지 외부 LLM에 전달하면 민감정보의 사용 범위가 넓어집니다.

02 설계와 구현 과정

  1. 증상 표현과 약품 설명이 달라도 연결할 필요가 있었습니다

    사용자가 말하는 증상과 약품 효능에 적힌 단어는 같은 뜻이어도 다를 수 있었습니다. 개인화에는 임신 여부·복용약·기저질환도 필요했습니다.

    판단 자연어 표현을 연결하는 일과 건강 프로필의 조건을 판단하는 일은 구분할 수 있었습니다. 둘을 모두 외부 AI에 맡기면 필요 이상의 프로필 정보까지 전달하게 됩니다. 약품 효능을 Weaviate에 저장해 증상과 의미가 가까운 정보를 찾도록 했습니다. 질문에 따라 약품 탐색·복약 위험·섭취량 정보를 처리하는 경로도 나눴습니다.

  2. 건강 프로필은 내부 코드에서 판단하도록 분리했습니다

    임신 여부·복용약·기저질환을 이용한 개인화가 필요했지만, 이 필드들을 외부 LLM 입력에 함께 넣을 필요는 없었습니다.

    판단 증상 표현을 이해하는 데 AI를 활용하되, 프로필을 사용하는 판단은 입력과 규칙을 직접 관리할 수 있는 내부 코드에 두기로 했습니다. 해당 프로필 필드는 외부 LLM 입력에서 제외하고, 내부 판단을 증상 검색 결과와 연결해 개인화 정보를 제공하도록 구현했습니다.

자연어 증상으로 약품 정보를 탐색하면서도 임신 여부·복용약·기저질환 필드는 외부 LLM 입력에서 제외했습니다. AI에 전달할 정보와 내부 코드가 판단할 정보를 구분한 구현 경험입니다.
