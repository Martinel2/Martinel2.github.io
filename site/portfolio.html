주로 PDF로 제공되는 논문을 지식으로 활용하려면, Markdown으로 변환 시 표의 수치와 수식이 먼저 보존돼야 했습니다. 이를 위해 변환 결과를 AI로 고치는 과정에서 생기는 누락을 추적하고, 원본 배치와 내용 유형에 맞춰 처리 경로를 나눴습니다.

2026.07 — 2026.09

PDF 변환 오픈 소스 : AnyDoc, DoclingLLM APIPythonLLM-as-a-Judge

01 배경

논문 PDF를 서비스의 지식으로 활용하려면 본문뿐 아니라 표·수식·그림도 보존한 Markdown이 필요했습니다.

02 실험과 개선 과정

  1. 손상 영역 선택 복원과 탐지 누락 확인

    문제 상황 오픈소스로 PDF를 Markdown으로 변환하자 표의 행·열 관계와 수식이 손상됐습니다. 전체를 다시 처리하지 않고 잘못 변환된 부분만 복원할 방법이 필요했습니다.

    시도와 결과 손상된 부분만 골라 AI로 복원한 뒤, 복원한 부분과 그대로 둔 부분을 각각 평가했습니다. AI가 복원한 96개 중 85개는 평가를 통과했습니다. 하지만 복원하지 않은 부분을 확인하자 오류·누락이 107개 남아 있었습니다. OCR 대조를 추가한 별도 실험에서는 통과율을 80.00%에서 97.53%로 높였지만, 정상인 내용 50개도 수정 대상으로 골랐고 처리 단계의 시간 합은 약 12분 35초였습니다.

    판단 무엇을 복원할지 고르는 과정에서 오류를 놓치고, 이를 보완하는 검사에도 비용이 들었습니다. 손상 탐지에 의존하게되고, 그에 따른 비용이 드니 원본 페이지 전체를 AI가 읽게 하는게 더 나을 수도 있겠다고 판단했습니다.

  2. 전체 페이지 AI 변환의 표·수식 오류와 비용 확인

    문제 상황 손상된 부분만 고르는 방식은 오류를 놓쳤고, OCR 대조를 추가하면 정상 내용도 수정 대상으로 선택하면서 검사 시간과 비용이 늘었습니다.

    시도와 결과 논문 PDF 25개(415쪽)를 전체 AI로 처리했을 때 내용 보존 통과율은 91.92%였습니다. 하지만 표·수식의 값과 구조가 모두 맞은 비율은 58.84%였고, 모든 페이지를 처리하는 호출 부담도 컸습니다.

    판단 모든 내용을 같은 방식으로 AI에 맡기기보다, 본문은 필요한 부분에만 AI를 쓰고 표·수식은 각각의 구조를 보존할 수 있는 입력을 제공해야겠다고 판단했습니다. 본문과 표, 수식의 처리 경로를 나누고, 본문을 빠르게 추출하면서 필요한 부분만 AI로 복원할 방법을 모색했습니다.

  3. 본문 추출 비교와 AnyDoc 적용

    문제 상황 페이지 전체를 AI로 처리해도 표·수식 오류가 남았고, 모든 본문까지 모델에 보내는 부담이 컸습니다. 표·수식은 별도로 복원하면서 본문은 빠르게 추출할 방법이 필요했습니다.

    시도와 결과 Threads에서 PDF 변환 도구 AnyDoc을 알게 됐고, GitHub의 Docling 대비 평가 결과를 보고 기존 실험에 쓰던 PDF 4개(30쪽)로 비교했습니다. 기존 Docling 처리 기록은 134.19초였고, AnyDoc의 텍스트 추출은 1.68초로 약 80배 짧았습니다. Docling은 OCR과 표 분석까지 포함한 시간이었습니다. AnyDoc 결과에서는 한 문서의 글자가 깨졌고, PDF 내부에 글자 코드를 실제 문자로 연결하는 정보가 빠진 것이 원인이었습니다.

    판단 처리 범위가 달라 전체 변환이 80배 빨라졌다고 볼 수는 없지만, 본문을 빠르게 추출하는 데 활용할 가치가 있다고 판단했습니다. 표와 수식은 이미 별도로 복원하고 있었으므로 그 과정은 유지하고, 본문 추출을 AnyDoc으로 바꾸되 글자가 깨진 페이지는 AI로 보완하기로 했습니다. 읽는 순서가 섞인 페이지도 AI로 복원하고, 그림은 원본을 보존했습니다.

01 배경

사용자 요청에 맞는 작업과 답변 근거를 안정적으로 선택하기 위해, 라우팅부터 RAG까지 Jev의 적용 범위를 넓혀가며 검증했습니다.

02 실험과 개선 과정

  1. 요청 분류 성능 비교와 RAG 적용 결정

    문제 상황 사용자 질문이 문서 편집으로 분류되는 등, 요청에 맞지 않는 작업으로 이어지는 문제가 있었습니다. 작업 종류와 부가 조건을 더 정확하고 빠르게 고를 방법이 필요했습니다.

    시도와 결과 9/14일 출시된 선택형 판단 모델 Jev를 사용자 요청을 질문, 문서 편집, 문서 생성, 폴더 정리 등으로 나누는 라우팅에 적용했습니다. 모델이 판단한 98개 요청에서 작업 종류와 부가 조건을 모두 맞힌 수는 기존 JSON 방식 77개, 같은 선택지를 받은 GPT-5-nano 63개, Jev 81개였습니다. 판단시간 중앙값 또한 기존 8.967초에서 Jev 0.658초로 개선된 결과를 보였습니다.

    판단 Jev는 정확도와 속도 모두 가능성을 보였습니다. 이 결과를 바탕으로, 기존 검색에서 해결하지 못한 답변 근거 선택에도 Jev를 적용해보기로 했습니다.

  2. 전체 근거 검사로 평가 질문 90건의 근거 충족

    문제 상황 질문 원문을 검색에 사용하고 의미 점수의 비중을 높여, 질문 110개에서 정답 자료가 첫 번째에 나오는 경우를 50개에서 57개로 향상시켰습니다. 하지만 이는 일부 편향된 실험이였으며, 새로운 질문에서도 필요한 근거를 안정적으로 고르는 문제는 해결하지 못했습니다.

    시도와 결과 라우팅에서 효과를 확인한 Jev가 검색 단계에서 놓친 근거도 찾을 수 있는지 확인했습니다. 테스트용 위키에 저장된 근거 2,020개를 검색으로 거르지 않고 모두 검사한 뒤, 기존 검색과 동일하게 최대 8개를 반환했습니다. 의역을 인정한 의미 평가에서 답이 있는 90개 질문의 근거 충족률은 기존 24/90건(26.7%)에서 Jev 90/90건(100%)으로 높아졌습니다. 답이 없는 질문 10개에는 모두 근거를 반환하지 않았습니다. 처리시간 중앙값은 기존 1.511초, Jev 5.338초였습니다. Jev는 80개씩 나눈 26개 묶음을 최대 4개씩 병렬 처리했습니다.

    판단 전체 근거를 보면 필요한 정보를 찾을 수 있었지만, 질문마다 모든 근거를 검사하는 방식은 문서가 늘수록 호출량도 늘어납니다. 또한 테스트에 편향이 있다고 판단되어 변수를 통제할 필요가 있었습니다. 이 테스트 위키의 90문항 결과만으로 적용 범위를 정하지 않고, 검색으로 후보를 먼저 줄인 뒤 Jev가 답변 근거를 선택하도록 바꾸기로 했습니다.

  3. 동일 500개 후보 비교에서 근거 충족률 87.50% 달성

    문제 상황 전체 근거 실험은 질문마다 26묶음을 호출해야 했습니다. 또한 특정 기술 문서에 질문이 몰려 있었고, 질문에 문서 제목이 포함돼 있었습니다. 기존 검색은 일부 페이지만 살피는 반면 Jev는 전체 근거를 봤으므로, 정확도 차이가 모델의 판단력 때문인지 접근 범위 때문인지 구분하기 어려웠습니다. 후보를 줄이는 것과 함께 비교 조건도 맞춰야 했습니다.

    시도와 결과 논문 9편으로 질문 100개를 새로 만들고, 기존 평가 질문은 재사용하지 않았습니다. 한 논문에서 답을 찾는 질문 63개, 두 논문을 연결해야 하는 질문 17개, 답이 없는 질문 20개로 구성하고 질문·정답·필수 사실을 실행 전에 고정했습니다. 중복 근거를 합친 뒤 BGE-M3와 BM25로 최대 500개 후보를 한 번만 추려 두 방식에 같은 본문과 정보를 제공했습니다. 기존 선택기도 후보에 속한 모든 페이지를 볼 수 있게 했고, 양쪽 모두 최대 8개 근거의 본문을 자르지 않고 반환하도록 맞췄습니다. 정답은 검색과 Jev 입력에서 제외했습니다. GPT와 Gemini는 방식 이름과 상대 결과를 보지 않고 각각 채점했으며, 실행 순서도 번갈아 배정했습니다. 이 조건에서 GPT 기준 근거 충족률은 기존 53/80건(66.25%)에서 Jev 70/80건(87.50%)으로 높아졌고, Gemini도 52/80건에서 74/80건으로 개선을 확인했습니다. 답 없는 질문에 근거를 반환한 경우는 20건에서 1건으로 줄었습니다. 후보 추리기를 포함한 처리시간 중앙값은 기존 0.431초, Jev 9.090초였습니다. 이때 Jev는 묶음을 순차 처리했습니다.

    판단 같은 후보와 반환 조건에서도 Jev의 근거 선택이 더 나아, 검색은 후보 수집을 맡고 Jev는 최종 근거 판단을 맡는 구조를 유지하기로 했습니다. 다만 공개 논문과 직접 작성한 질문의 결과이므로 일반적인 정확도로 단정하지 않았습니다. 순차 호출의 대기 시간을 줄이기 위해 다음에는 후보 수와 묶음 처리 방식을 조정하기로 했습니다.

  4. 300개 후보·4병렬 처리로 대기 시간 단축

    문제 상황 Jev로 근거 선택은 개선됐지만, 후보를 최대 500개까지 순차 처리하면 준비와 선택 시간의 중앙값이 9.090초로 기존 방식의 0.431초보다 길어졌습니다. 정확도를 유지하면서 대기 시간을 줄여야 했습니다.

    시도와 결과 후보 처리 시간을 줄이기 위해 후보를 상위 300개로 줄이고 최대 4개 묶음을 병렬 처리해 시간은 2.251초로 줄었고, 필요한 근거를 모두 고른 질문은 70개에서 73개로 늘었습니다.

    판단 시간을 줄였음에도 2.251초로 기존 0.431초보다는 느렸습니다. 후보를 더 줄이고 더 많은 묶음의 병렬 처리 시도를 고려해봤으나, 필요한 근거가 250위보다 아래에 존재하는 사례가 있어 해당 안은 기각했습니다. 비록 처리 시간이 늘었지만, 정확도가 서비스의 핵심이라고 판단하여 Jev를 채택하기로 결정했습니다.

02 판단과 구현 과정

  1. 사용자 정의 작업 지침의 작성·게시 기능 구현

    문제 상황 회의록 정리처럼 사용자마다 반복하는 작업이 달라, 개발자가 모든 기능을 미리 추가하는 데는 한계가 있었습니다.

    판단 기능을 하나씩 추가하는 대신, 사용자가 자연어로 작업 지침을 정의하고 재사용하도록 하기로 했습니다. AI가 만든 지침은 사용자 검토 전까지 제안으로만 다루기로 했습니다.

    구현 자연어 요청을 재사용 가능한 Markdown Skill로 구체화했습니다. 사용자가 초안을 검토·수정하고 최종 게시할 때 Skill과 버전을 저장하도록 구현했습니다.

    확인한 결과 게시 전에는 Skill이나 임시 초안을 DB에 남기지 않고, 최종 게시한 작업 지침을 이후 작업에서 재사용할 수 있게 했습니다.

  2. 작업 지침의 권한·승인 우회 방지 검증

    문제 상황 사용자가 만든 작업 지침과 참고 문서에 개인정보나 권한·승인을 우회하는 지시가 포함될 수 있었습니다. 같은 의도를 표현하는 방식이 다양했고, 검토한 초안도 게시 전에 사용자가 수정할 수 있었습니다.

    판단 명확한 위험과 권한 검사는 코드가 맡고, 표현을 바꾼 우회 의도는 LLM으로 검사하기로 했습니다. 검토 후 사용자가 내용을 수정할 수 있으므로 이전 검사 결과만으로 게시를 허용하지 않기로 했습니다.

    구현 입력과 참고 문서에 규칙 검사를 적용하고, LLM이 지적한 위험 문구가 실제 원문에 있는지 서버에서 대조했습니다. 참고 문서는 권한과 원문을 검사한 뒤 필요한 구조만 모델에 전달했습니다. 최종 게시 시에는 수정된 내용으로 검사를 다시 수행했습니다. 위험 문구는 원문에서 자동으로 삭제하지 않고, 사용자가 재생성을 선택한 경우에만 제거한 뒤 결과를 다시 검사하도록 했습니다.

    확인한 결과 차단된 입력의 원문과 문제 위치를 사용자에게 보여주도록 했습니다. 사용자는 차단 이유를 보고 직접 수정하거나 재생성을 선택할 수 있게 됐습니다.

  3. 변경 미리보기와 사용자 승인 후 반영

    문제 상황 Skill을 검토해 게시했더라도 실행할 때 바뀔 문서와 내용은 별도로 확인해야 했습니다. 작업 지침의 게시만으로 실제 문서 변경까지 승인한 것으로 볼 수는 없었습니다.

    판단 지침 게시와 실제 문서 변경은 별도의 승인으로 나누기로 했습니다. 작업 분류는 라우터가 맡고 실행기는 정해진 작업을 수행하되, 무엇이 바뀌는지는 사용자가 확인하도록 했습니다.

    구현 편집은 수정 전후 차이를, 폴더 정리는 만들 폴더와 이동할 문서를 계획으로 보여줬습니다. 출력 형식과 수정 범위는 코드로 검사하고, 승인한 변경만 실행하도록 연결했습니다.

CASE 05Pilltip / 데이터 파이프라인 · GPT Batch API

의약품 정제 파이프라인 - 예상 $200 대비 실제 $11.18로 변환

어려운 의약품 정보를 이해하기 쉬운 표현으로 바꾸기 위해 데이터 정제 파이프라인을 구축했습니다. 완전히 같은 문장과 의미가 같은 문장을 차례로 통합하고, 누락된 5%는 성분별 주의사항을 정제해 보완했습니다. 고유 문장을 변환해 각 약품에 다시 연결하면서 실제 API 지출 $11.18로 처리했습니다.

2025.07 — 2025.07

데이터 파이프라인Fuzzy MatchingGPT Batch API데이터 분석

01 배경

약 4만 4천 건의 약품 원문을 사용자가 이해하기 쉬운 설명으로 변환하는 기능을 만들었습니다.

02 문제 분석과 구현 과정

  1. 완전 일치 문장 중복 제거

    문제 상황 약 4만 4천 건, 1GB 규모의 원문을 모두 변환하면 API 비용이 약 $200으로 예상됐습니다. 예산 안에서 전체 약품의 설명을 제공할 방법이 필요했습니다.

    시도와 결과 약품 원문 100개를 조사해 약 70%가 중복되는 내용임을 확인했고, 표본 분석과 작업 계획으로 전처리 기간 7일을 확보했습니다. 원문을 문장 블록으로 나눠 완전히 일치하는 문장은 하나로 통합하고, 각 약품과 문장 블록의 연결을 남겼습니다.

    판단 약품 수를 줄이는 대신 같은 문장을 한 번만 변환해 재사용하기로 했습니다. 다만 문자열이 완전히 같지 않은 중복도 남아, 다음에는 표현이 달라도 의미가 같은 문장을 구분하기로 했습니다.

  2. 의미가 같은 문장 통합

    문제 상황 완전 일치 중복을 제거해도 어미나 표현만 다른 문장은 별개의 변환 대상으로 남았습니다. 같은 주의사항을 다시 변환하지 않으면서 용량과 숫자의 차이는 보존해야 했습니다.

    시도와 결과 어미 정리와 유사도 비교를 활용해 의미가 같은 문장을 묶었습니다. 약품 ID와 문장 블록 ID의 연결을 유지하고, 용량과 숫자는 따로 처리해 표본을 직접 확인했습니다. 완전 일치와 의미 중복 정리를 거쳐 변환 대상은 1GB에서 326MB로 줄었습니다.

    판단 문자열이 비슷하다는 이유만으로 합치기보다, 약품별 정보와 수치를 보존하면서 같은 설명을 재사용하도록 했습니다. 중복 제거로 끝내지 않고 누락된 약품 정보도 확인하기로 했습니다.

  3. 성분별 주의사항 정제로 누락된 5% 보완

    문제 상황 앞선 처리에서 약 5%의 정보가 누락돼, 중복을 줄인 데이터만으로는 모든 대상의 설명을 채울 수 없었습니다.

    시도와 결과 누락된 항목을 확인하고, 같은 성분의 주의사항이 공통된다는 점에 착안했습니다. 누락된 성분별로 데이터를 모아 정제한 뒤 추가 처리해 부족한 주의사항을 보완했습니다.

    판단 누락된 항목을 제외하지 않고 성분 단위로 보완하기로 했습니다. 약품별로 반복 처리하기보다 공통된 성분별 주의사항을 활용해 설명의 제공 범위를 유지했습니다.

  4. GPT Batch API 일괄 변환과 약품별 재연결

    문제 상황 변환 비용을 최대한 줄일 필요가 있었고, 중복은 제거했으나, 모델 비용도 줄일 수 있는 방법을 모색해야 했습니다.

    시도와 결과 서비스 사용 중 즉시 응답해야 하는 작업이 아니므로 일괄 처리의 대기 시간을 허용했습니다. 고유 문장을 GPT Batch API로 변환한 뒤, 보존한 약품 ID와 문장 블록 ID의 연결을 이용해 각 약품에 결과를 다시 연결했습니다. 전체 원문 변환에 예상했던 약 $200 대비 실제 API 지출 $11.18로 변환을 마쳤습니다.

    판단 중복 제거와 성분별 누락 보완, Batch 변환을 함께 사용해 약품의 범위를 줄이지 않고 기능을 구현했습니다.

03 개선한 처리 흐름

04 결과와 배운 점

변환 대상 1GB → 326MB · 실제 API 지출 $11.18

전체 원문을 처리할 때 예상한 약 $200 대비 실제 API 지출 $11.18로 변환을 마쳤습니다. 완전 일치·의미 중복 제거로 변환 대상을 줄이고, 누락된 5%는 성분별 주의사항 정제로 보완했습니다. 설명을 제공할 약품의 범위를 줄이지 않고, 정제한 고유 문장의 변환 결과를 재사용해 예산 안에서 기능을 구현했습니다.

CASE 06Pilltip / AI Agent · 개인정보 유출 방지

복약 챗봇 - 건강 프로필을 외부 AI 입력에서 분리

RAG 기반 AI 오케스트레이션으로 복약 관련 정보를 안내하는 AI 챗봇을 앱에 탑재할 수 있도록 했습니다. 사용자 증상에 맞는 의약품 탐색과 프로필에 따른 판단을 나눴습니다. 모델의 언어 해석 능력을 활용하면서 민감한 프로필을 사용하는 범위는 코드로 관리했습니다.

2025.09 — 2025.9

Spring AIWeaviateRAGAI Orchestration

01 배경

사용자가 자연어로 증상을 질문하면 약품 정보를 찾고, 개인 건강 프로필에 맞는 정보를 제공하는 복약 챗봇을 구현했습니다.

02 설계와 구현 과정

  1. 증상과 약품 효능을 연결하는 의미 검색 구현

    문제 상황 사용자가 말하는 증상과 약품 효능에 쓰인 단어는 같은 뜻이어도 달랐습니다. 단어가 일치하지 않아도 관련 정보를 연결할 방법이 필요했습니다.

    판단 자연어 증상과 약품 효능을 연결하는 일에는 의미 검색을 사용하고, 질문에 필요한 정보를 제공하도록 처리 경로를 나누기로 했습니다.

    구현 약품 효능을 Weaviate에 저장해 증상과 의미가 가까운 정보를 찾도록 했습니다. 질문에 따라 약품 탐색·복약 위험·섭취량 정보를 처리하는 경로를 구성했습니다.

    확인한 결과 증상을 자연어로 입력해 약품 정보를 탐색하고, 질문에 맞는 처리 경로로 연결하는 기능을 구현했습니다.

  2. 건강 프로필의 내부 처리와 외부 AI 입력 분리

    문제 상황 개인화에는 임신 여부·복용약·기저질환이 필요했지만, 이 프로필까지 외부 LLM에 전달하면 민감정보의 유출이 우려되었습니다.

    판단 증상 표현을 이해하는 일과 건강 프로필의 조건을 판단하는 일을 분리하기로 했습니다. 프로필을 사용하는 판단은 입력과 규칙을 직접 관리할 수 있는 내부 코드에 두기로 했습니다.

    구현 임신 여부·복용약·기저질환 필드를 외부 LLM 입력에서 제외했습니다. 내부 코드의 프로필 판단을 증상 검색 결과와 연결해 개인화 정보를 제공하도록 구현했습니다.

    확인한 결과 해당 건강 프로필 필드를 외부 LLM 입력에 포함하지 않으면서, 내부에서는 개인화 판단에 사용할 수 있도록 처리 경로를 분리했습니다.

03 개선한 처리 흐름

04 결과와 배운 점

증상 의미 검색과 건강 프로필의 내부 판단 분리

자연어 증상으로 약품 정보를 탐색하면서도 임신 여부·복용약·기저질환 필드는 외부 LLM 입력에서 제외했습니다. AI에 전달할 정보와 내부 코드가 판단할 정보를 구분한 구현 경험입니다.

결과의 범위 · 트레이드오프

프로필 조건이 바뀌면 내부 코드도 수정해야 하는 단점이 존재하나, 개인 정보 유출을 원천 차단하는 것이 우선이였기 때문에 AI에게 해당 작업을 위임하지 않고 일을 처리하도록 했습니다.
