PROJECT OVERVIEW

Fruition

올린 문서를 LLM이 Wiki로 정리하고, RAG로 원문 근거를 찾아 답하거나 자연어로 문서를 편집하는 AI 워크스페이스입니다. 지금은 AWS EKS에 배포해 QA를 진행하고 있습니다.

시작 계기

팀원이 겪던 문서 관리의 불편함을 디자인 싱킹으로 구체화하며 시작했습니다. 문서를 저장만 해 두고 정작 필요할 때 찾지 못하는 불편을 없애는 게 목표였습니다.

팀 구성과 내 역할

MY ROLEAI

PDF 변환, Wiki 생성, RAG 검색·근거 답변, 문서 편집 Agent 등 AI 기능 전체

  • AI 기능 전체 리드PDF문서 변환 파이프라인 구축, Wiki의 구조 설계 및 생성, 유지보수 구현, 근거를 포함한 질의와 문서 편집을 수행하는 Agent 등 AI 기능 전반의 설계와 평가를 리드하고, 구현은 AI 코딩 도구로 진행했습니다.
  • MSA 설계 기여초안은 기능별로 서비스를 나눴습니다. 그런데 그렇게 나누면 DB에 걸리는 부하는 그대로고, 서비스를 거치는 호출만 늘어 분산하는 의미가 없었습니다. 그래서 데이터 소유권을 기준으로 나누자고 제안했고, 팀원·멘토와 서비스 경계와 통신 방식을 논의해 최종 구조를 함께 완성했습니다.

CASE 01 AI Agent · RAG · Jev

RAG 근거 선택 - 충족률 66.25% → 91.25% 개선과 Jev 최적화로 처리시간 87% 단축

Fruition은 사용자가 올린 문서를 근거로 답하는 서비스라, 근거가 틀리면 답변 전체를 믿을 수 없게 된다고 생각했습니다. 앞서 요청을 질문, 편집 등으로 분류하는 라우팅에서 Jev의 정확도와 속도 개선을 확인했고, 이를 계기로 답변 근거 선택에도 적용해 근거 충족률을 66.25%에서 91.25%로 높였습니다. 늘어난 처리 시간은 후보 수와 병렬 처리 조정으로 줄였습니다.

CASE 03 AI Agent · 보상 복구 · 감사 이력

AI 작업 취소와 이미 저장한 변경의 복구

AI가 문서를 바꾸는 서비스에서 취소가 확실하지 않으면, 사용자는 AI에게 작업을 맡길 수 없다고 생각했습니다. 실행만 멈추면 이미 저장한 문서·폴더·Wiki·Skill 변경이 그대로 남아, 커밋한 변경까지 역순으로 되돌리는 경로를 만들었습니다. 이때 다른 작업이 정상적으로 남긴 기여는 지우지 않도록, 대상 기여만 빼고 복원했습니다.

CASE 04 PDF 문서 변환 · 데이터 파이프라인
