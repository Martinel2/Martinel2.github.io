01 배경

모델 폐기 여부를 확인하다 일부 기능이 사용자 선택과 달리 하드코딩된 모델로 실행되는 문제를 발견했고, 변경 범위가 저장소 5개로 넓어졌습니다. 에이전트가 실제로 없는 문제를 보고하거나 계획 일부만 구현할 수 있었고, 대화에서 바뀐 결정이 원래 이슈에 남지 않아 검토 기준도 어긋났습니다.

해결하면 얻는 것

여러 서비스의 변경이 같은 결정과 기준을 따르도록 하고, 미완료 구현과 잘못된 리뷰 지적이 추가 작업으로 이어지는 것을 줄이고자 했습니다.

02 범위 결정과 검토 방식

  1. 관련 이슈를 묶고 설계 결정은 직접 수행

    문제 상황 모델 설정 문제에서 서비스 간 변경으로 범위가 커졌고, 개별 수정마다 정책을 정하면 결정이 흩어질 수 있었습니다.

    시도와 결과 관련 이슈를 범위별로 묶고 에이전트에게 선택지와 장단점을 제시하게 했습니다. 저는 정책을 선택하고 계획서와 검증 기록을 남긴 뒤 구현하도록 했습니다.

    판단 탐색과 구현은 에이전트에 맡기되 서비스 동작과 범위의 결정은 직접 유지했습니다.

  2. 별도 세션에서 결정 기록을 기준으로 리뷰

    문제 상황 구현 세션이 스스로 검토하고 있었고, 원래 이슈에는 결정 전 내용이 남아 검토 기준이 달랐습니다.

    시도와 결과 새 세션에서 저장소별 검토를 진행하고 부분 일치 대신 일치·불일치를 판정하게 했습니다. 계획서와 대조한 뒤 원래 이슈에도 결정 기록을 남겨 기준을 맞췄습니다.

    판단 결정은 대화에서 끝내지 않고 이후 검토자가 찾을 수 있는 곳에 기록해야 했습니다.

  3. 리뷰 지적 재확인과 미완료 이슈 재개

    문제 상황 리뷰어는 로그가 약 60일 남는다고 주장했고, 이미 하기로 한 기능도 새 이슈로 추적하려 했습니다.

    시도와 결과 다시 확인하니 로그 전용 S3 이전 버전 규칙으로 실제 보관은 약 31일이었습니다. 이후 파일·줄 근거를 요구했습니다. 닫힌 이슈 31개 중 미완료 7개를 찾아 원래 이슈를 다시 열었습니다.

    판단 지적을 고치기 전에 사실인지 확인하고, 새 일을 늘리기보다 합의한 요구를 마무리했습니다.

04 결과와 배운 점

2일간 PR 78개 생성, 닫힌 이슈 31개 중 미완료 7개 발견
